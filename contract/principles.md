# 開發原則

寫 code 時逐條套用，送驗前逐條自查，違反的當場修掉。專案 CLAUDE.md 另有要求時從之。

設計時假設下一個改這段 code 的是**照抄者**：只看得到自己打開的檔、會照抄最近的例子、走最短能編譯的路。好的設計讓照抄者從一個檔看起來對的改法，對整個 repo 也對。

## 設計

- **先沿用**：新增函式、類別、工具前，先在 repo 找既有的並沿用；寫法跟著周圍 code 走。
- **最小改動**：用能解決問題的最小 diff。同一個決定（設定值、規則、對照表）只在一處決定，其他地方拿結果用。
- **先減再加**：加功能或重構前，先刪死 code、多餘的檢查、沒人用的參數，再在更簡單的基礎上加。只為已觀察到的用法設計（YAGNI）。改完應該比改之前簡單。
- **rule of three**：同一段邏輯出現第三次、或兩處必須永遠一起改，才抽成共用。抽出來的東西要讓讀者少追一層。
- **單一職責**：名稱能完整說出它做的事；描述要用到「並且」就拆。函式約 30 行內、參數 3 個內。
- **減少讀者負擔**：盯兩件事——從問題到答案要追幾層、腦中要記住多少隱藏狀態。收掉淺層包裝（只有一個呼叫端的包裝、只有一個實作的轉接層、原樣轉傳參數的方法）。狀態範圍越小越好：純函式 > 區域變數 > 欄位 > 模組層級 > 全域；能推導的就推導。新讀者應該 30 秒內答得出「X 從哪來、誰能改 X」。
- **先定資料結構**：寫邏輯前先定核心型別與資料結構，把每個主要的存取方式走一遍；需要「之後再加個 map 或快取」代表結構選錯了。CI、lint、測試設施、共用型別這類讓之後每一步受益的東西先做。
- **用結構表達領域**：用對得上領域的結構取代散落的條件判斷——狀態機取代一堆布林旗標、型別化的模型取代鬆散的參數、對照表取代分散在各檔的 if/else。新功能讓既有的 if/else 再長一個分支，或多一個要跟另一個同步的旗標，就是該換結構的訊號。目前的寫法清楚、局部、不太會長大時，維持樸素的寫法。
- **改 API 就改完呼叫端**：專案內部的介面要改時，同一張單裡改完所有呼叫端、刪掉舊介面；只保護舊實作細節的測試換成驗新介面。有外部使用者依賴時（公開 API、其他團隊、已發佈的套件），照專案 CLAUDE.md 的相容政策。
- **parse, don't validate**：驗證、型別轉換、錯誤處理集中在系統邊界——CLI 參數、設定檔、外部 API、從 DB 或檔案讀進來的資料——在那裡把外部資料解析成型別，邊界內信任型別。業務邏輯寫成純函式；DB、外部 API、時間等依賴由建構時注入，連線與 driver 只出現在 adapter 層。
- **讓型別擋錯**：意義不同但底層型別相同的值（例如使用者 id 與訂單 id）給不同的型別。有權威的 schema（migration、OpenAPI、protobuf）就從它產生型別。動態語言用 dataclass、pydantic 這類有型別的模型。
- **冪等（idempotent）**：會被重試、排程或中斷的操作（cron、migration、背景工作、批次匯入），跑兩次、或上次跑到一半當掉，最後狀態都一樣：讀現況、比對目標、只補差異；檔案先寫到暫存路徑再改名；留下的鎖或半成品，下一次要能判斷它已過期。
- **先消除共享，再談加鎖**：幾個執行者可能同時寫同一個檔案、分支、鍵或狀態時，先讓它們各寫各的，到讀取或回報時才合併。只有「一份共用的寫入目標」本身是不變條件時，才用結構化的方式排隊（鎖檔、分階段、單一寫入者）。
- **新需求當作一開始就有**：把新需求接進既有設計時，先讀完受影響的檔，照「如果一開始就知道這個需求會怎麼設計」來改，並把改動傳到所有相關的型別、文件、範例。
- **沒有前例的設計先比較**：專案裡沒有前例的介面、互動或架構決定，先做 2–3 個方向不同的版本比較再定：只關係到 code 結構的用 `jill425:code-design`，關係到使用體驗的開原型單。
- **命名用領域詞**：取自專案 CLAUDE.md 或需求的業務用語，讓名稱本身說明用途。
- **體驗優先**：實作方便跟使用體驗衝突時選體驗。「使用者」是用這份產出的人：畫面的終端使用者、import 這個函式庫的同事、下一個維護的工程師。少做幾項但做精，細節到位（操作回饋、錯誤狀態、對齊、轉場）。

## 測試

- **測行為，不測實作**：測試驗使用者看得到的東西——回傳值、錯誤、能讀回來的狀態、對外部的影響（送出的請求、寫入的資料列、發出的訊息）。用兩個想像的改動檢查每個測試：
  - **把行為改壞**（回錯的值、少做或多做一次副作用）：測試要變紅。
  - **只改內部、結果不變**：測試要維持綠。

  期望值從需求推出來；斷言契約承諾的，不多也不少。送給外部服務的內容是行為，呼叫了哪個內部函式是實作。呼叫端會依它分支的錯誤型別是契約，錯誤訊息的確切字句不是。

## 交付

- **TDD**：先寫會失敗的測試 → 實作 → 轉綠。測試要有鑑別力：拿掉實作就紅、放回就綠（mutation 檢查），由 tester 驗。
- **計畫好的改寫直接收斂到目標**：有明確階段的重寫或遷移，以最後的目標架構為準，直接朝它改。中間可以暫時壞，但事先寫明在哪一段、範圍多大、怎麼還原；動到的地方保留檢查，全部完成時完整驗證。
- **數字要說得出來**：報告或依據任何量到的數字（速度、錯誤率、評估分數）之前，說得出是什麼限制了它、跑了幾次、波動多大，並排除它量到別的東西（錯誤、快取、沒執行的程式碼）的可能。效能數字照 `ticket-kinds.md`〈量數字的檢查〉。
- **做工具，不手工**：大量相似的修改、分析、檢查，寫腳本或 codemod 來做、來驗，讓別人能重跑。先手做一個學會做法，再寫工具，拿它重跑那一個並跟手做的結果比對。只寫夠用的小腳本；工作會延續到之後就 commit 進 repo。
- **Done = 對真實依賴跑過**：真實 DB、真實流程；只有連不到的外部第三方才 mock。連線類基礎設施開機就驗（如 `SELECT 1`），連不上當場 fail。
- **一次交付完整**：每個欄位與資料都是真值、當下可用。
