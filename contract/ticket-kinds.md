# 單的種類：bug、調查、效能、原型

功能單照 `task-contract.md`〈單的格式〉即可。其他四種在建單或執行前讀對應的一節；四段格式都一樣，以下是額外的規定。

## bug

- `## 背景` 附**重現**：觸發的指令或操作步驟、實際輸出、期望輸出——建單前實際跑過、親眼看到錯。重現不出來就改開調查單，目標是找到能穩定重現的條件。
- `## Test 方法` 第一條是重現測試：`- [ ] 重現：<測試或指令> 修正前失敗、修正後通過`。它就是「測試有鑑別力」要驗的那個測試。

## 調查

- `## 目標` 寫要回答的問題，一條一個。
- `## Test 方法` 每個問題一條：`- [ ] <問題>：結論寫在單上的〈結論〉，附檔案與行號、重現指令或量測輸出`。證據要到「跑過」以上，到不了的照實標等級。
- 探查用的腳本只寫在 scratchpad；結論需要改 code 時，另開功能或 bug 單，兩張單互相連結。
- **查執行時的問題**（記憶體一直漲、閒置時 CPU 一直轉、畫面偶爾閃）：先在出問題的介面上抓真實資料——CPU profile、heap snapshot、trace、log——再推理。資料量大時交給 subagent 化簡，主線只收結論：熱點函式、從洩漏物件到根的引用鏈、沒有輸入卻一直觸發的迴圈。加 log 或觀測點實際跑，證明推論出來的機制真的會發生，再對回 `檔案:行`。
- **分析別人給的 profile 或 trace 檔**：檔案是固定資料，直接讀。大的先轉成能查詢的形式（例如每個 sample 一列寫進 sqlite），再查佔最多時間的 frame、走到熱點。對得回原始碼的 frame 才算結論。有修改前後兩份時用來確認；只有一份時，結論標為「這份資料最支持的推論」。

## 效能

- `## 背景` 附**基準**：要做出的主張（例如「匯出在 6 萬列資料上 p50 快 30%」）、量測指令、環境、目前的數字。建單前實際量過，照下方〈量數字的檢查〉確認它可信。
- `## Test 方法` 第一條：`- [ ] <量測指令> 在 <同樣環境> 下達到 <目標>（每邊至少 5 次、交錯跑，取中位數）`；另加一條「既有測試全綠」。
- **執行是一個循環**，一次一個假設：
  1. 先做好量測工具並固定：一個指令印出數字、錯誤數、實際做了多少工作。工具先 commit，之後只用它量。
  2. 每個假設說出具體的機制（「把 X 移出啟動路徑，因為它擋住第一次繪製」）。
  3. 改 → 用固定的工具量前後 → 跑既有測試。前後中位數的差距大於兩邊各自的範圍（最小到最大）、而且測試全綠才保留，一個保留的改善一個 commit；否則完整還原。
  4. 每次嘗試，不論保留或還原，都寫進〈結論〉的嘗試紀錄。
  5. 達到目標就停。連續 3 個假設都沒有保留，就換一類方向再試；換過一次仍沒有，就停下並在〈結論〉列出剩下的想法。目標維持原樣。行為出錯的改善要還原，數字不變但更簡單的改動要保留。
- **量數字的檢查**（基準、每次量測、最後報告都適用）：
  - **為什麼不是兩倍快？** 說出限制它的是什麼（CPU 核心、鎖、磁碟、網路、量測工具本身），從 profile 或系統數據取得。
  - **兩邊設定一樣嗎？** 兩邊都照正式環境的設定跑；一邊用預設值時，比的是設定，不是實作。
  - **有錯誤嗎？工作真的做了嗎？** 數錯誤與失敗的回應；確認計時範圍內真的發了請求、寫了資料、用了結果。被拒絕的請求和沒執行的程式碼都很快。
  - **重現得了嗎？** 兩邊交錯各跑至少 5 次，報中位數與範圍；差距小於波動就是沒有可量測的差異。
  - **對使用者重要嗎？** 量一個小函式時，同時量使用者實際等待的整條路徑，報它佔整體的比例。
  - **報告**：先給結論（變快、變慢、沒有可量測差異、無法判定），再給數字、單位、次數、範圍、限制因素。說不出限制因素、或沒確認錯誤與「工作真的做了」，結論就是無法判定。

## 原型

- `## 目標` 寫要決定的問題，以及**比較標準**。標準在動手前寫好。
- `## Test 方法`：`- [ ] 每個方案都照比較標準實測，結果與選擇寫在單上的〈結論〉，附量測輸出或截圖路徑`。
- 原型 code 只放在原型分支或 scratchpad。選定後另開功能單實作，兩張單互相連結。
