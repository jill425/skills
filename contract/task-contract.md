# Task 契約

task 單的格式、生命週期與後端。建單（`jill425:task-plan`）、執行（`jill425:task-dev`、`jill425:task-multi-run`）、驗收（`jill425:task-tester`）開工前讀本檔；依情況再讀同目錄的：

| 情況 | 讀 |
|---|---|
| 要派 subagent | `dispatch.md` |
| 要寫 code | `principles.md` |
| 建或做 bug、調查、效能、原型單 | `ticket-kinds.md` 對應的一節 |
| 驗「測試有鑑別力」那條 | `tdd-evidence.md` |
| 新增一種 task 後端 | `backends/README.md` |

本檔與同目錄的檔都用相對路徑互指：`dispatch.md` 是本目錄的檔，`../scripts/` 是 plugin 的腳本目錄。

專案 CLAUDE.md 與本檔衝突時專案優先（DoD、測試與驗收指令、架構、命名、技術選型都可覆寫）；Invariants 只有標「專案可覆寫」的能覆寫，且專案 CLAUDE.md 要寫明替代的驗收方式。

## Invariants

1. **做事與驗收分離。** 驗收交給隔離的 `jill425:task-tester`，判定不採實作者自評。（專案可覆寫）
2. **資料結構不臆測。** 資料表、欄位、API 欄位的名稱只取自專案文件、schema 檔或使用者確認。
3. **`## Test 方法` 至少一條客觀可測的條件**，驗收只依它判定、附實際跑過的證據。（專案可覆寫）
4. **破壞性操作先問人**：`rm -rf`、`git push --force`、`git reset --hard`、刪分支、DB 寫入與 DDL——先說明動什麼、影響什麼，等回覆再做。（本機開發／測試用的資料庫不在此限）
5. **正式環境只讀。** 要寫正式環境的資料就停下交給人；分不清是測試還是正式環境時，一律當正式環境。
6. **以 code 為準。** 說明 code 怎麼運作、決定怎麼改、判定有沒有做到之前，先讀目前分支上實際的檔案，結論附 `檔案:行`。單上的描述、文件、註解、commit 訊息、記憶都只是線索；跟 code 對不上時以 code 為準，並指出哪裡不一致。

## 單的格式

一張單由四段構成，標題用動詞開頭的簡短描述。單是寫給沒參與對話的人看的：只讀這張單和 repo 就要做得出來。

```markdown
## 背景
（為什麼開這張單：觸發背景、要解決的問題，以及規劃時已定案的決策與假設。）

## 目標
（做完的樣子：做什麼、為誰、成功長什麼樣。）
- 範圍外：（明列不做的事；無則省略此行）

## 做法
（限制與已定案的決策：要沿用的模組、不能碰的介面、選定的方案。逐步實作留給執行者。
SQL、migration、部署這類「照抄才安全」的操作才附 fenced code block，標明在哪跑。無則留「無」。）
- 影響範圍：（會動到的資料表、API、共用模組；`jill425:task-multi-run` 靠它判斷兩張單會不會互相影響。都不碰就省略此行）

## Test 方法
- [ ] 可驗證、客觀可測的完成條件
（寫出實際的驗證語法：跑哪個指令、期望輸出、檢查哪個檔案或狀態。）
```

- **必填**：`## 背景`、`## 目標`、`## Test 方法`。相依關係記在 adapter 指定的地方。
- **顆粒度**：一張單是一個**垂直切片**：端到端、做完就能實際跑起來看見結果。判準是「做完後能看到什麼在跑？」，答不出來就重切。專案的第一張單是 walking skeleton。
- **種類**：每種工作都開單，單就是這件工作的追蹤紀錄。種類只決定完成長什麼樣：

| 種類 | 用在 | 產出 |
|---|---|---|
| 功能 | 新的或不同的行為 | code |
| bug | 修既有缺陷 | code，加上重現測試 |
| 調查 | 找原因、搞懂現況、評估可行性 | 單上的〈結論〉 |
| 效能 | 讓一個量得到的數字變好 | code，加上〈結論〉裡的前後數字 |
| 原型 | 比較幾種做法、試可行性 | 單上的〈結論〉；原型 code 不合併 |

功能單照本節即可；其他四種在建單或執行前讀 `ticket-kinds.md` 對應的一節。

## Test 方法

`## Test 方法` 是建單方與驗收方的共同契約（invariant 3）：驗收依它逐條判定，每條附實際跑過的證據。只有人或 `jill425:task-plan` 能改它：使用者在開發中當場定案的變更，由執行者照 `jill425:task-plan`〈修改既有單的 `## Test 方法`〉第 3 步更新；執行者自己覺得某條不適用時，寫〈驗收標準需重新確認〉執行備註。

**程式類單的標準條**：由 `jill425:task-plan` 附上，任何語言都一樣：

`- [ ] 測試有鑑別力：拿掉實作後新增的測試全紅（斷言失敗）、放回全綠（驗法見 tdd-evidence.md）`

純文件、設定、基礎設施、調查、原型單不附；`refactor` 與效能單裡行為不變的優化，以既有測試全綠為證。

**範圍**：程式類單（調查、原型單除外）另外盤點「單上沒要求的 code」。它不影響驗收判定：列出來，由使用者決定刪或留。
- 盤點這張單的 diff 新增的每一個公開方法、參數、選項、錯誤型別與它的屬性、輸入檢查、抽象層、enum 值，各自對到單上的一句（目標、做法或 Test 方法）。
- 對不到的，要說得出「不做會讓單上哪一句出錯」才算在範圍內；說不出的，連同只為它而寫的測試，列為「單上沒要求的 code」。
- 單上寫明範圍外的情境，對應的 code 一律列出。
- 開發中由 `jill425:check-plan` 逐切片列出，執行者刪掉自己說不出理由的；驗收者再獨立盤點一次，列在驗收結果。

## 執行期產出

落點與寫法（追加或就地改）照 adapter。

**單是追蹤紀錄**：日後的人只看單和 code，就要看得懂 code 為什麼長這樣。照著單做的部分由 code 承載（分支、commit、diff）；code 跟單上預想的不同、或做了單上沒定的選擇，寫成執行備註。

**執行備註**，每筆標類別；前四種寫清原本、實際、為什麼：

1. **範圍變動**：多做或少做了目標裡的東西。
2. **推翻假設**：背景裡的前提不成立。
3. **偏離做法**：實作跟 `## 做法` 寫的不同，例如改用別的模組、換了方案、碰了做法說要保留的地方。
4. **決策**：`## 做法` 沒指定、有兩種以上可行做法，而且選擇會影響介面、資料結構、依賴或模組歸屬時，寫選了哪個、為什麼不選另一個。
5. **驗收標準需重新確認**：某條 Test 方法已不適用，附建議的新標準。驗收者遇到這類時標「⚠ 驗收標準需人工確認」，不判未過。
6. **續做錨點**：執行中途要停時寫，讓接手的人能接著做：做到哪一步、哪些 Test 方法已跑過、下一步、未 commit 的改動在哪、踩到的坑。只有最新一份有效，只在單處於「執行中」時讀。

**結論**（調查、效能、原型單）：只有最新一份有效。

```markdown
## 結論

- <對應 `## 目標` 的每個問題，一條一個答案>：<證據：`檔案:行`、重現指令、量測輸出；證據等級>
- 選擇（原型單）：<選了哪個方案、依比較標準的結果>
- 數字（效能單）：<結論；量測指令；前 → 後（中位數、範圍、次數）；限制因素>
- 嘗試紀錄（效能單）：<每次嘗試一列：假設、改了什麼、前、後、測試、保留或還原、commit>
- 後續：<需要另開的單，連結>
```

**驗收結果**：

```markdown
## 驗收結果

- [x] <Test 方法原文> — <一行證據：跑的指令與實際輸出>
- [ ] <Test 方法原文> — 未過：<期望 vs 實際>
  - 現象：<錯誤訊息或具體輸出>
  - 修復：<哪個檔、改什麼、建議指令>

<全條通過時：標明「完成」>

**單上沒要求的 code（不影響判定，由使用者決定刪或留）**
- 盤點了 <N> 項。`<檔案:行>` <內容>：對不到單上的任何一句；只為它而寫的測試 `<檔案:行>`（沒有就寫「無」）

**⚠ 缺漏／風險（不影響判定）**
- 〔<證據等級>〕<Test 方法沒寫到但明顯該做的、沒同步的文件、風險>：<怎麼確認的>；修法：<具體做法>（無則整段省略）
```

**證據等級**：每個主張標它的根據走到哪一級。10 分鐘內寫得出腳本驗證的，推到「跑過」；到不了的照實標。
1. **推測**：只是說說，沒有任何指認。
2. **指認**：指到真實的 `檔案:行` 或函式庫原始碼。
3. **推演**：一步步走過失敗路徑，說得出會不會走到。
4. **跑過**：寫了腳本或測試呼叫真實 code，結果印出來了。
5. **重現**：在跑起來的 app 上重現。

**查證結論**：`jill425:code-how`、`jill425:code-why` 為某張單而跑時，摘要（附 `檔案:行` 或出處）由呼叫的角色寫進單：建單時寫進 `## 背景`；執行中發現跟單上的理解不同時，寫成〈推翻假設〉或〈決策〉執行備註。

## 生命週期

五個狀態，各自怎麼表示照 adapter。

```
待辦 ──(指名或依序挑選)──> 執行中 ──(實作完成)──> 待測 ──(驗收)──┬──(全條通過)──> 完成
                              ▲                                      │
                              └────── 修正重做 <───────(未過)────────┘
```

- **開始**：單在待辦，且相依的單都已完成；由使用者指名，或由 `jill425:task-multi-run` 依序挑選。一次只做一張，開工前重讀它。
- **轉待測**：由執行者做完收尾（`jill425:task-dev` 步驟 3）、全部 Test 方法重跑全綠後才轉。
- **修正重做**：在原單、原分支回到執行中，由同一個執行者原地修。
- **完成**：驗收全條通過即完成，不需人再確認。PR／MR 照團隊流程 merge；專案 CLAUDE.md 寫明「完成即自動 merge」時，由主線照 adapter 的指令 merge。
- **需要人決定**：驗收 3 輪仍未過、標了「⚠ 驗收標準需人工確認」、需要人做的操作（invariant 4、5），或會改變行為、API、schema、資料語意的發現。執行者停下來問（`jill425:task-dev`〈需要人決定時〉），等到回答才往下做。
- **卡住**：無人值守時沒有人能回答，需要人決定的單停在原狀態、原因留在單上；`jill425:task-multi-run` 跳過它、相依它的單與受同一個決定影響的單，最後在彙總列出。

## 決策紀錄

影響 code 樣子的決定寫在單上（執行備註〈偏離做法〉〈決策〉）。**流程上的決定**記在本機，用 `../scripts/log-decision.sh` 記一行（參數見腳本開頭）：

| 角色 | 要記的決定 |
|---|---|
| `task-multi-run` | 選了哪張、跳過哪張、判定卡住、派工用的場景與模型、merge、收回報告後核對不符 |
| `task-dev` | 停下來寫續做錨點、範圍外的發現、每條檢查發現的處置、派驗收者用的模型 |
| `task-tester` | 需要判斷的判定：反向驗證要人工看斷言時的結論、「此標準不可驗證」、缺漏的證據停在推測 |

一行一個決定，「為什麼」用白話寫，「證據」只放指標（commit sha、`檔案:行`、驗收第幾輪、指令）。

## git commit

格式 `#<id> <type>(<scope>): <subject>`，type ∈ feat|fix|refactor|test|docs|chore|perf，scope 為模組名可省。

- `#<id>` 是 task 編號（issue 後端：issue 編號；local-files：frontmatter `id`）；不屬於任何單的雜務可省。
- 1–2 行、subject ≤72 字元（含前綴）、英文祈使句；訊息到 subject 為止，不加 trailer（含 `Co-Authored-By`）。
- 用 `git commit -m` 寫訊息：`#` 開頭的 subject 在編輯器裡會被 git 當成註解刪掉。plugin 的 hook 會在 commit 後檢查以上各條。
- commit、PR／MR、issue 只引用隊友拿得到的東西。

## Task 後端

單存在 GitHub issue（`backends/github-issues.md`）、GitLab issue（`backends/gitlab-issues.md`）或專案的 `tasks/`（`backends/local-files.md`）。哪個專案用哪個，記在本機的 `~/.claude/task-backends/projects.md`（不存在就從 `backends/projects.template.md` 建立）。

**開工第一步是認後端**：查登記表 → 讀對應的 adapter → 照它的機制存取。查無此專案時問使用者 task 單放在哪（GitHub repo、GitLab repo 或本機 `tasks/`；issue 可以跟 code 不同 repo），補登記後再開工。
