# Task 契約（規格層）

task 單的格式、生命週期、後端機制。由 `jill425:task-plan`／`jill425:task-run`／`jill425:task-executor`／`jill425:task-tester` 開工時讀取。
本檔的 `<plugin>` 指 plugin 根目錄＝本檔所在目錄的上一層。
專案 CLAUDE.md 與本檔衝突時專案優先（DoD、測試與驗收指令、架構、命名、技術選型皆可覆寫），唯〈Invariants〉例外。

**本檔與 task 存在哪裡無關**：段落格式、生命週期、怎麼算完成、交接原則在任何後端都一樣。換後端只換 adapter，不動本檔。

## Invariants

下列規則專案 CLAUDE.md 只能覆寫標「專案可覆寫」的，且須明寫替代的驗收方式；其餘一律照本檔。

1. **做事與驗收分離。** 驗收交給隔離的 `jill425:task-tester`，判定不採實作者自評。（專案可覆寫）
2. **資料結構不臆測。** 資料表、欄位、API 欄位的名稱只取自專案文件、schema 檔或使用者確認。
3. **`## Test 方法` 至少一條客觀可測的條件**，驗收只依它判定、附實際跑過的證據。（專案可覆寫）
4. **破壞性操作先問人**：`rm -rf`、`git push --force`、`git reset --hard`、刪分支、DB 寫入與 DDL——先說明動什麼、影響什麼，等回覆再做。（本機開發／測試用的資料庫不在此限）
5. **正式環境只讀。** 要寫正式環境的資料就停下交給人；分不清是測試還是正式環境時，一律當正式環境。
6. **先讀 code，不憑描述或記憶。** 說明 code 怎麼運作、決定怎麼改、判定有沒有做到之前，先讀目前分支上實際的檔案，結論附 `檔案:行`。單上的背景與做法、文件、註解、commit 訊息、記憶、這個 session 稍早讀過的印象，都只是線索，可能已經過時；跟 code 對不上時以 code 為準，並指出哪裡不一致。

## 交接原則

1. **契約優先**：格式以本檔為準，必填段落一律寫齊。
2. **脈絡隨單走**：task 從何而來、規劃決策與假設都寫進 `## 背景`；後續執行者只看得到單和 repo。
3. **每張單乾淨 context 對錨**：一次只處理一張單，開工前重讀它對焦。

---

## 派 subagent 的慣例

任何角色派 subagent（`jill425:task-executor`、`jill425:task-tester`、`jill425:code-impact` 的攻擊者，或臨時的查詢）都照這幾條：

1. **brief 固定五項**：使用者的原始目標（原話）、單號、要讀的檔（給路徑）、不准做的事、回報格式。
2. **給路徑，不貼內容**：讓 subagent 自己讀，派的一方不把檔案內容貼進 brief。
3. **每次派新的**：重做、追問、接下一張都派新的 subagent，把上一輪的報告與驗收結果貼進新 brief；不續用舊的，舊的會帶著上一輪的指令殘留。
4. **要隔離就開 worktree**：會並行改檔、或要拿掉實作來驗時，各自在 `<scratchpad>` 開 worktree，用完移除。
5. **報告不等於事實**：派的一方採信前自己確認關鍵事實——看 `git log`／diff、單的狀態、跑一次報告裡說通過的關鍵指令。
6. **不問人**：subagent 遇到需要人決定的事，寫進單上的續做錨點，回報卡住；不停下來等回覆。

## 決策紀錄

無人值守時，人事後要看得懂每個重要決定的理由，不只看結果。決定分兩層記：

- **影響 code 樣子的決定**（選了哪個做法、偏離了單上的做法）寫在**單上**，用執行備註的〈偏離做法〉〈決策〉兩類。單是給日後追蹤的人看的，這類決定一定要跟著單走。
- **流程上的決定**（選哪張、跳過、卡住、merge、需要判斷的驗收結論）寫在本機的決策紀錄，`<plugin>/scripts/log-decision.sh <單號> <角色> <決定> <為什麼> <證據> <結果>` 記一行，誰記什麼如下：

| 角色 | 要記的決定 |
|---|---|
| `task-run` | 選了哪張、為什麼跳過哪張、判定卡住、merge、收回報告後核對不符 |
| `task-executor` | 停下來寫續做錨點、範圍外的發現（做法的選擇與偏離寫在單上，不寫這裡） |
| `task-tester` | 需要判斷的判定：反向驗證 exit 2 讀斷言後的結論、「此標準不可驗證」、缺漏的證據等級停在推測 |

- **記決定，不記動作**：跑了測試、讀了檔不記；選了 A 不選 B、跳過、換方向才記。
- **一句話**：「為什麼」用白話寫，「證據」只放指標（commit sha、`檔案:行`、驗收第幾輪、指令），不寫長文。
- **位置**：`$(git rev-parse --git-common-dir)/jill425/decisions.tsv`，跟鎖檔放在一起；在 git 目錄裡，不進版控，所有 worktree 共用同一份。腳本會印出路徑。
- `jill425:task-run` 的彙總附上紀錄檔路徑與這一輪記了幾筆；`jill425:task-reflect` 回顧時讀它。

## 模型分配

依**場景**決定模型，不依 session 是什麼模型。派 subagent 時照下表設 `model` 與 `effort`；使用者在本機 `~/.claude/jill425-models.md` 寫了某個場景的那一行，就以那一行為準（格式見 `<plugin>/contract/models.template.md`）。

原則：判斷重、出錯代價高的用強的模型；大量讀檔、照指示執行的用快的模型；互相檢查的兩方用**不同**的模型，盲點才不會重複。

### 實作與驗收

| 場景 | 模型 | effort | 理由 |
|---|---|---|---|
| 執行（一般）：功能、bug、原型單 | `sonnet` | `high` | 範圍明確的實作，照單做 |
| 執行（困難）：見下方判斷 | `opus` | `high` | 設計判斷多、出錯代價高 |
| 執行（文件）：純文件、設定單 | `sonnet` | `medium` | |
| 驗收 | 跟這張單的執行者**不同**：執行者是 `opus` 就用 `sonnet`，否則用 `opus` | `high` | 換一個模型才看得到執行者的盲點 |

**困難**的判斷由 `jill425:task-run` 派工前讀單決定，符合任一條就算：
- 單的種類是調查或效能。
- 做法或目標要新增、改變跨模組的介面，新增模組，或碰到併發、資料遷移、複雜的演算法。
- 這張單已經驗收未過一次以上（重做時升級）。

### 審查、設計、理解與回顧

| 場景 | 誰派 | 模型 | effort |
|---|---|---|---|
| 攻擊者 A | `jill425:code-impact` | `opus` | `high` |
| 攻擊者 B | `jill425:code-impact` | `sonnet` | `high` |
| 設計者 A | `jill425:code-design` | `opus` | `high` |
| 設計者 B | `jill425:code-design` | `sonnet` | `high` |
| how 探索者 | `jill425:code-how` | `sonnet` | `medium` |
| how 解說者 | `jill425:code-how` | `opus` | `high` |
| why 調查者 | `jill425:code-why` | `sonnet` | `medium` |
| why 彙整者 | `jill425:code-why` | `opus` | `high` |
| reflect 審視者 | `jill425:task-reflect` | `sonnet` | `high` |
| reflect 彙整者 | `jill425:task-reflect` | `opus` | `high` |

### 主線

`jill425:task-run` 的主線只選單、派工、核對、彙總，用 `sonnet` 就夠；主線的模型由啟動 session 的人決定（例如 `claude -p --model sonnet`），本表管不到。

- 模型值只能是 `opus`、`sonnet`、`haiku`、`fable`；`effort` 只能是 `low`、`medium`、`high`、`xhigh`、`max`。
- 指定的模型被拒絕時，改用跟 session 同一個（不設 `model`），並在報告裡說明。
- 派工時把選了哪個場景、哪個模型記一筆決策紀錄。

## Task 後端（本機登記，可換）

adapter 檔在 `<plugin>/contract/backends/`，一個後端一檔：

| 後端 | 單存在哪 | 適合 |
|---|---|---|
| `github-issues` | GitHub repo 的 issue（`gh`） | 用 GitHub 協作，task 與 PR／分支綁在一起 |
| `gitlab-issues` | GitLab repo 的 issue（`glab`） | 用 GitLab 協作，task 與 MR／分支綁在一起 |
| `local-files` | 專案根目錄 `tasks/` 底下的 Markdown 檔 | 單人、不想依賴平台 |

**哪個專案用哪個後端，記在 `~/.claude/task-backends/projects.md`**（本機登記表，以 git remote 對號）。後端是個人工具設定，只住在本機登記表——專案檔案是與人共用的，指向本機路徑的設定對隊友沒有意義。登記表不存在時，從 `<plugin>/contract/backends/projects.template.md` 複製一份。

**每個角色開工的第一步是認後端**：查登記表 → 讀對應的 adapter 檔 → 照它的機制存取。查無此專案時**問使用者 task 單放在哪**：GitHub repo（`owner/repo`）、GitLab repo（網址或 `group/project`），或本機 `tasks/`。issue 可以放在跟 code 不同的 repo。依答案選 adapter、記下 task 位置，補登記後再開工。

### adapter 檔要回答的六件事（新增後端時照這六題寫）

1. 單存在哪；怎麼列出待辦；怎麼讀一張的全文與既有記錄
2. 怎麼開一張新單（含標題與 body 的落點）
3. 執行備註／驗收結果各寫到哪，是覆寫還是追加
4. 下方五個生命週期狀態各用什麼表示、怎麼轉
5. 「完成」在這個後端是什麼動作；相依的前一張還沒合併時，下一張怎麼開工
6. 該後端特有的命名與關聯慣例（分支、編號、連結）

adapter 只寫**機制**；格式與規則在本檔。狀態名一律用本檔的字（如「完成」），再補該後端等於什麼動作。

## task 單的固定內容

不論後端，一張單都由這四段構成。標題用動詞開頭的簡短描述。

```markdown
## 背景
（為什麼開這張單：觸發背景、要解決的問題，以及規劃時已定案的決策與假設。「為什麼」只寫在這裡。）

## 目標
（做完的樣子：做什麼、為誰、成功長什麼樣。）
- 範圍外：（明列不做的事；無則省略此行）

## 做法
（限制與已定案的決策：要沿用的模組、不能碰的介面、選定的方案。不寫逐步實作。
SQL、migration、部署這類「照抄才安全」的操作才附 fenced code block，標明在哪跑。無則留「無」。）

## Test 方法
- [ ] 可驗證、客觀可測的完成條件 1
- [ ] 可驗證、客觀可測的完成條件 2
（寫出實際的驗證語法：跑哪個指令、期望輸出、檢查哪個檔案／狀態。）
```

必填：`## 背景`、`## 目標`、`## Test 方法`（至少一條，空的或不可驗證的視為不合規）。相依關係不寫在 body，落點依 adapter。

**自我完備**：單是寫給沒參與對話的人看的，只讀這張單和 repo 就要做得出來。

**顆粒度**：一張單是一塊端到端、做完就能實際跑起來看見結果的切片（〈開發原則〉「垂直切片」）。判準：**做完後能看到什麼在跑？**答不出來就重切。多張單是成本，不是預設。

**單的種類**：每種工作都開單，單就是這件工作的追蹤紀錄。種類只決定「完成長什麼樣」，四段格式都一樣：

| 種類 | 用在 | 產出 |
|---|---|---|
| 功能 | 新的或不同的行為 | code |
| bug | 修既有缺陷 | code，加上重現測試 |
| 調查 | 找原因、搞懂現況、評估可行性 | 寫在單上的〈結論〉 |
| 效能 | 讓一個量得到的數字變好 | code，加上量測前後的數字 |
| 原型 | 比較幾種做法、試可行性 | 寫在單上的〈結論〉；原型 code 不合併 |

功能單照本節上面的格式。其他四種另有規定，見下。

**bug 類單**（修既有缺陷）：四段照舊，另加兩點。
- `## 背景` 附**重現**：觸發的指令或操作步驟、實際輸出、期望輸出——建單前實際跑過、親眼看到錯。重現不出來就不開修正單，改開調查單，目標是找到能穩定重現的條件。
- `## Test 方法` 第一條是重現測試：`- [ ] 重現：<測試或指令> 修正前失敗、修正後通過`。它就是〈TDD 證據〉要驗鑑別力的那個測試。

**調查單**（找原因、搞懂現況、評估可行性）：
- `## 目標` 寫要回答的問題，一條一個。
- `## Test 方法` 每個問題一條：`- [ ] <問題>：結論寫在單上的〈結論〉，附檔案與行號、重現指令或量測輸出`。結論的證據要到〈證據等級〉的「跑過」以上，到不了的照實標等級。
- 不改專案的 code；探查用的腳本放 scratchpad。結論需要改 code 時，另開功能或 bug 單，並在兩張單互相連結。
- **查執行時的問題**（記憶體一直漲、閒置時 CPU 一直轉、畫面偶爾閃）：不從原始碼推理，先在出問題的那個介面上抓真實的資料——CPU profile、heap snapshot、trace、log。資料量大時交給 subagent 化簡，主線只收結論：熱點函式、從洩漏物件到根的引用鏈、沒有輸入卻一直觸發的迴圈。相信之前先證明機制：加 log 或觀測點實際跑，確認推論出來的原因真的會發生。最後對回原始碼的 `檔案:行`。
- **分析別人給的 profile 或 trace 檔**：檔案是固定的資料，讀它，不重跑。大的先轉成能查詢的形式（例如每個 sample 或 frame 一列寫進 sqlite），再查佔最多時間的 frame、走到熱點。對不回原始碼的 frame 還不算結論。有修改前後兩份可以比對時用來確認；只有一份時，結論標為「這份資料最支持的推論」，不標為確定的原因。

**效能單**（讓一個量得到的數字變好）：
- `## 背景` 附**基準**：要做出的主張（例如「匯出在 6 萬列資料上 p50 快 30%」）、量測指令、環境、目前的數字。建單前實際量過，照下面〈量數字的檢查〉確認這個基準可信。
- `## Test 方法` 第一條：`- [ ] <量測指令> 在 <同樣環境> 下達到 <目標>（每邊至少 5 次、交錯跑，取中位數）`；另加一條「既有測試全綠」。
- **執行是一個循環**，一次只試一個假設：
  1. 先做好量測工具並固定下來：一個指令就印出數字、錯誤數、實際做了多少工作。工具本身先 commit，之後不再改它。
  2. 每個假設都要說出具體的機制（「把 X 移出啟動路徑，因為它擋住第一次繪製」），不是「試試加快取」。
  3. 改 → 用固定的工具量前後 → 跑既有測試。數字的改善超過誤差、而且測試全綠才保留，一個保留的改善一個 commit；否則完整還原。
  4. 每次嘗試，不論保留或還原，都寫進〈結論〉的嘗試紀錄。
  5. 達到目標就停；連續幾次沒進展先換方向再試，剩下的想法都不划算才停。不放寬目標來湊數字。正確性和簡單優先於數字：讓行為出錯的改善要還原，數字不變但更簡單的改動要保留。
- **量數字的檢查**（基準、每次量測、最後報告都適用）：
  - **為什麼不是兩倍快？** 說出限制它的是什麼（CPU 核心、鎖、磁碟、網路、或量測工具本身），要從 profile 或系統數據取得，不從讀 code 推測。
  - **兩邊都照正式環境的設定跑嗎？** 一邊用預設值時，比的是設定，不是實作。
  - **有沒有錯誤？工作真的做了嗎？** 數錯誤與失敗的回應；確認計時範圍內真的發了請求、寫了資料、用了結果。被拒絕的請求通常很快，沒執行的程式碼也很快。
  - **重現得了嗎？** 兩邊交錯各跑至少 5 次，報中位數與範圍；差距小於每次之間的波動，就是沒有可量測的差異。
  - **對使用者重要嗎？** 只量一個小函式時，同時量使用者實際等待的整條路徑，報它佔整體的比例。
  - **報告**：先給結論（變快、變慢、沒有可量測差異、無法判定），再給數字、單位、次數、範圍、限制因素。說不出限制因素、或沒檢查錯誤與「工作真的做了」，結論就是無法判定。

**原型單**（比較幾種做法、試可行性）：
- `## 目標` 寫要決定的問題，以及**比較標準**。標準在動手前寫好，避免做完再挑對自己有利的標準。
- `## Test 方法`：`- [ ] 每個方案都照比較標準實測，結果與選擇寫在單上的〈結論〉，附量測輸出或截圖路徑`。
- 原型 code 放在原型分支或 scratchpad，不合併。選定後另開功能單實作，兩張單互相連結。

### Test 方法的地位

`## Test 方法` 是規劃方與驗收方的共同契約（invariant 3）：

- 驗收**只依它**逐條判定，每條附實際跑過的證據。
- 只能由人或 `jill425:task-plan` 定案修改；執行角色只能在執行備註提出申請（見下）。

## 執行期產出

| 類別 | 誰寫 | 何時寫 |
|------|------|--------|
| **執行備註** | 執行 | 只在下列六種情況，否則不寫 |
| **結論** | 執行 | 調查、效能、原型單完成工作時 |
| **驗收結果** | 驗收 | 每輪驗收 |

落點與寫法（追加或就地改）由 adapter 決定。

**單是這件工作的追蹤紀錄**：日後的人只看單和 code，就要看得懂 code 為什麼長這樣，不會在兩者之間看到說不通的分歧。所以 code 跟單上預想的不同、或做了單上沒定的選擇，都要記；照著單做的部分不用記，由 code 承載（分支、commit、diff）。

**執行備註只收六種**，每筆標類別；前四種寫清原本／實際／為什麼：

1. **範圍變動**：多做或少做了目標裡的東西。
2. **推翻假設**：背景裡的前提不成立。
3. **偏離做法**：實作跟 `## 做法` 寫的不同，例如改用別的模組、換了方案、多碰了做法說不能碰的地方。
4. **決策**：`## 做法` 沒有指定、有兩種以上可行的做法，而且選擇會影響 code 的樣子（介面、資料結構、依賴、放在哪個模組）時，寫選了哪個、為什麼不選另一個。
5. **驗收標準需重新確認**：某條 Test 方法已不適用，附建議的新標準。出現這類時驗收角色不判未過，改標「⚠ 驗收標準需人工確認」，由人或 `jill425:task-plan` 定案後再驗。
6. **續做錨點**：執行中途要停（使用者說暫停、session 要結束、要換人接手）時寫，讓沒參與的人能接著做。內容：做到哪一步、哪些 Test 方法已在本機跑過、下一步要做什麼、未 commit 的改動在哪、踩到的坑。只有最新一份有效——local-files 就地覆寫、轉待測時刪除；issue 後端追加 comment，最新一則為準。只在單處於「執行中」時讀它。

**結論的格式**（調查、效能、原型單）：落點依 adapter，跟執行備註放在一起，只有最新一份有效。

```markdown
## 結論

- <對應 `## 目標` 的每個問題，一條一個答案>：<證據：`檔案:行`、重現指令、量測輸出；證據等級>
- 選擇（原型單）：<選了哪個方案、依比較標準的結果>
- 數字（效能單）：<結論；量測指令；優化前 → 優化後（中位數、範圍、次數）；限制因素>
- 嘗試紀錄（效能單）：<每次嘗試一列：假設、改了什麼、前、後、測試、保留或還原、commit>
- 後續：<需要另開的單，連結>
```

**驗收結果的格式**（任何後端都一樣）：

```markdown
## 驗收結果

- [x] <Test 方法原文> — <一行證據：跑的指令／實際輸出>
- [ ] <Test 方法原文> — 未過：<期望 vs 實際>
  - 現象：<錯誤訊息或具體輸出>
  - 修復：<哪個檔、改什麼、建議指令>

<全條通過時：標明「完成」>

**⚠ 缺漏／風險（不影響判定）**
- 〔<證據等級>〕<Test 方法沒寫到但明顯該做的、沒同步的文件、風險>：<怎麼確認的>；修法：<具體做法>（無則整段省略）
```

缺漏／風險寫進單裡（不只口頭回報），但與判定分開、不影響通過與否。

**證據等級**（缺漏／風險與 `jill425:code-impact` 共用）：每條標它的根據走到哪一級，便宜就往下推：
1. **推測**：只是說說，沒有任何指認。
2. **指認**：指到真實的 `file:line` 或函式庫原始碼。
3. **推演**：一步步走過失敗路徑，說得出會不會走到。
4. **跑過**：寫了腳本或測試呼叫真實 code，結果印出來了。
5. **重現**：在跑起來的 app 上重現。

只到「推測」的照實標，不包裝成定論。

## 生命週期與檢核點

五個狀態，任何後端都一樣；各自怎麼表示看 adapter。

```
待辦 ──(指名或依序挑選)──> 執行中 ──(實作完成)──> 待測 ──(驗收)──┬──(全條通過)──> 完成
                              ▲                                      │
                              └────── 修正重做 <───────(未過)────────┘
```

- **開始條件**：單在待辦，且相依的單皆已完成；由使用者指名，或由 `jill425:task-run` 依序挑選。
- **修正重做**在原單、原分支回到執行中，由 `jill425:task-run` 自動接續，不回待辦、不需重新指定。
- **完成**由驗收全條通過決定，不需人再確認。issue 後端的 PR／MR 照團隊流程 merge；專案 CLAUDE.md 寫明「完成即自動 merge」時，才由執行角色 merge。
- **卡住**：驗收第 3 輪仍未過、或標「⚠ 驗收標準需人工確認」的單，停在原狀態、原因留在單上；`jill425:task-run` 跳過它與相依它的單，繼續做其他的，最後在彙總裡列出。
- 每次轉待測前（含重做）先跑送驗前 review（見下）。

## 開發原則

寫 code 時逐條套用，送驗前逐條自查，違反的當場修掉。專案 CLAUDE.md 另有要求時從之。

### 設計

- **先沿用**：新增任何函式、類別、工具前，先在 repo 找既有的並沿用；寫法跟著周圍 code 走。
- **最小改動**：用能解決問題的最小 diff，少幾行勝過「優雅」的樣板。同一個決定（設定值、規則、對照表）只在一處決定，其他地方拿結果用。
- **先減再加**：加功能、重構、重寫之前，先刪掉死 code、多餘的檢查、沒人用的參數，再在更簡單的基礎上加。照實際的用法設計，不為想像出來的邊界情況加驗證或防禦。改完的地方應該比改之前更簡單。
- **抽象要有理由**：同一段邏輯出現第二次先不抽；出現第三次、或兩處必須永遠一起改，才抽成共用。抽出來的東西要讓讀者少追一層，不是多一層。
- **單一職責**：名稱能完整說出它做的事；描述要用到「並且」就拆。函式約 30 行內、參數 3 個內。
- **減少讀者負擔**：可維護性就是讀者要花多少力氣才看得懂。盯兩件事：從問題到答案要追幾層、腦中要記住多少隱藏的狀態。只有一個呼叫端的包裝、只有一個實作的轉接層、原樣轉傳參數的方法，直接收掉。狀態的範圍越小越好：純函式勝過修改、區域變數勝過欄位、欄位勝過模組層級、模組層級勝過全域；能推導的就不要另外同步一份。新讀者應該 30 秒內答得出「X 從哪來、誰能改 X」。
- **先定資料結構**：寫邏輯之前先定核心型別與資料結構，把每個主要的存取方式走一遍；「之後再加個 map 或快取」代表結構選錯了。會讓之後每一步都受益的東西（CI、lint、測試設施、共用型別）先做。
- **用結構表達領域**：用一個對得上領域的結構取代散落的條件判斷——狀態機取代一堆布林旗標、型別化的模型取代鬆散的參數、對照表或 registry 取代分散在各檔的 if/else。新功能讓既有的 if/else 再長一個分支，或多一個要跟另一個保持同步的旗標，就是該換結構的訊號。目前的寫法已經清楚、局部、不太會長大時，維持樸素的寫法。
- **改 API 就改完呼叫端**：專案內部的介面要改時，同一張單裡改完所有呼叫端、刪掉舊的，不留相容層，也不「新增一個實作、舊的保持不動」。只保護舊實作細節的測試刪掉，改成驗新的介面。有外部使用者依賴時（公開 API、其他團隊、已發佈的套件）例外，照專案 CLAUDE.md 的相容政策。
- **驗證放在邊界**：驗證、型別轉換、錯誤處理集中在系統邊界——CLI 參數、設定檔、外部 API、從 DB 或檔案讀進來的資料。邊界內信任型別，不重複檢查。業務邏輯寫成純函式；DB、外部 API、時間等依賴由建構時注入，連線與 driver 只出現在 adapter 層。
- **讓型別擋錯**：外部資料在邊界解析成型別，之後只傳型別。意義不同但底層型別相同的值（例如使用者 id 與訂單 id）給不同的型別。有權威的 schema（migration、OpenAPI、protobuf）就從它產生型別，不手寫平行的一份。動態語言用 dataclass、pydantic 這類有型別的模型。
- **跑幾次結果都一樣**：會被重試、排程或中斷的操作（cron、migration、背景工作、批次匯入），跑兩次、或上次跑到一半當掉，最後的狀態都要一樣。做法是讀現況、比對目標、只補差異；檔案先寫到暫存路徑再改名；留下的鎖或半成品，下一次要能判斷出它已經過期。
- **先消除共享，再談加鎖**：幾個執行者可能同時寫同一個檔案、分支、鍵或狀態時，先問它們是不是真的需要同一份。不需要就各寫各的，到讀取或回報時才合併。只有「一份共用的寫入目標」本身是不變條件時，才用結構化的方式排隊（鎖檔、分階段、單一寫入者）。靠文字約定不算並行控制。
- **新需求當作一開始就有**：把新需求接進既有設計時，不要硬接上去。先讀完受影響的檔，問「如果一開始就知道這個需求，會怎麼設計」，照那個樣子改，並把改動傳到所有相關的型別、文件、範例。
- **沒有前例的設計先比較**：專案裡沒有前例的介面、互動或架構決定，先做 2–3 個方向不同的版本比較再定：只關係到 code 結構的用 `jill425:code-design`，關係到使用體驗、需要實際摸看看的開原型單。
- **命名用領域詞**：取自專案 CLAUDE.md／需求的業務用語，讓名稱本身說明用途。
- **體驗優先**：實作方便跟使用體驗衝突時選體驗。「使用者」是用這份產出的人：畫面的終端使用者、import 這個函式庫的同事、下一個維護的工程師。少做幾項但做精，細節要到位（操作回饋、錯誤狀態、對齊、轉場）。

### 測試

- **測行為，不測實作**：測試驗的是使用者看得到的東西——回傳值、錯誤、能讀回來的狀態、對外部的影響（送出的請求、寫入的資料列、發出的訊息）。私有函式、內部呼叫順序、中間資料都是實作。用兩個想像的改動檢查每個測試：
  - **把行為改壞**（回錯的值、少做或多做一次副作用）：測試要失敗，不然它什麼都沒證明。
  - **只改內部、結果不變**：測試要照樣通過，不然它綁死了實作，每次重構都要改。
  期望值從需求推出來，不從跑一次 code 得到；斷言契約承諾的，不多也不少。送給外部服務的內容是行為；呼叫了哪個內部函式是實作。呼叫端會依它分支的錯誤型別是契約，錯誤訊息的確切字句不是。

### 交付

- **垂直切片**：每張實作單是端到端跑得動的切片，第一張就是 walking skeleton。基礎設施併進第一個用到它的切片，由該切片真實驗證。
- **TDD**：先寫**會失敗的測試** → 實作 → 轉綠。測試先行，不事後補寫。測試要有鑑別力：拿掉實作就紅、放回就綠，由 tester 反向驗證（〈TDD 證據〉）。
- **計畫好的改寫直接收斂到目標**：有明確階段的重寫或遷移，以最後的目標架構為準，不為了讓每個中間狀態都完全可用而寫暫時的相容程式。中間可以暫時壞，但要事先說明在哪一段、範圍多大、怎麼還原；動到的地方保留檢查，全部完成時完整驗證。
- **數字要說得出來**：報告或依據任何量到的數字（速度、錯誤率、評估分數）做決定之前，說得出是什麼限制了它、跑了幾次、波動多大，並排除它量到別的東西（錯誤、快取、沒執行的程式碼）的可能。效能數字照〈單的種類〉效能單的〈量數字的檢查〉。
- **做工具，不手工**：不簡單的工作（大量相似的修改、分析、檢查）寫腳本或 codemod 來做、來驗，讓別人能重跑。先手做一個學會做法，再寫工具，拿它重跑那一個，跟手做的結果比對。只寫夠用的小腳本，不寫框架；工作會延續到之後就 commit 進 repo。
- **Done = 對真實依賴跑過**：真實 DB、真實流程；只有連不到的外部第三方才 mock。連線類基礎設施開機就驗（如 `SELECT 1`），連不上當場 fail。
- **一次交付完整**：每個欄位與資料都是真值、當下可用。

## git commit

格式 `#<id> <type>(<scope>): <subject>`，type ∈ feat|fix|refactor|test|docs|chore|perf，scope 為模組名可省。

- `#<id>` 是 task 編號（issue 後端：issue 編號；local-files：frontmatter `id`）。不明就問；只有不屬於任何單的雜務可省。
- 1–2 行、subject ≤72 字元（含前綴）、英文祈使句；訊息到 subject 為止，不加任何 trailer（含 `Co-Authored-By`）。
- 一律用 `git commit -m` 寫訊息：`#` 開頭的 subject 在編輯器裡會被 git 當成註解刪掉。plugin 的 hook 會在 commit 後檢查以上各條，不符就回報要你 amend。
- commit、PR／MR、issue 只引用隊友拿得到的東西。

## 送驗前 review

每次轉「待測」前，執行角色對該單相對基底分支的完整 diff 跑內建 `code-review`（level low：只回高信心的 correctness 問題）；接著跑內建 `simplify`，對照〈開發原則〉的「設計」與「測試」逐條檢查。碰 token、個資、DB 寫入的單再加 `security-review`。改到對外介面（API 的 request／response 欄位、訊息格式）、DB schema 或被多處共用的模組時，再加 `jill425:code-impact`（影響面分析加兩個攻擊者），它證出的風險與驗證過的攻擊發現當場修，證不出的照它的格式附在送驗回報。發現當場修完，**修完後重跑全部 Test 方法與 DoD 指令**，全綠才送驗；送驗之後不再另跑 review——tester 驗的就是最終的 code。

## TDD 證據（程式類單）

〈開發原則〉的 TDD 要證明的是**測試有鑑別力**：這張單新增的每個測試，拿掉實作就紅（斷言失敗），放回實作就綠。tester 用反向驗證判定，不看 commit 順序——順序證明不了「先寫」，鑑別力才是要的性質。

- **Test 方法標準條**：程式類單一律由 `jill425:task-plan` 附這條，任何語言都一樣：
  `- [ ] 測試有鑑別力：拿掉實作後新增的測試全紅（斷言失敗）、放回全綠（驗法見契約〈TDD 證據〉）`
- **基底**：local-files 是這張單第一個 `#<id>` commit 的上一個 commit；issue 後端是與整合分支的 merge-base。
- **pytest 專案**：在專案根目錄跑腳本（它在 scratchpad 開 worktree，不動工作目錄，跑完移除）：
  - local-files：`<plugin>/scripts/verify-tdd.py --id <id> --runner "<專案的 pytest 指令>" --workdir <scratchpad>/vt-<id>`
  - issue 後端：`<plugin>/scripts/verify-tdd.py --base <整合分支> --runner "<專案的 pytest 指令>" --workdir <scratchpad>/vt-<id>`

  `--runner` 取專案 CLAUDE.md 的測試指令（如 `uv run pytest`、`poetry run pytest`、`python -m pytest`）。未進版控但測試要用的檔（如金鑰檔）加 `--copy <path>`；根目錄的 `.env*` 自動帶過去。輸出表格貼進驗收結果當證據。
- **其他測試框架**（Jest、Vitest、Go、Flutter 等）：tester 照同樣的邏輯手動做，測試指令取專案 CLAUDE.md：
  1. `git worktree add --detach <scratchpad>/vt-<id> HEAD`，在裡面裝好依賴；未進版控的設定檔照需要複製過去。
  2. 對照基底的 diff，列出這張單新增的測試案例。
  3. 只跑這些測試：全綠才往下，否則判未過（有實作卻沒綠）。
  4. 把這張單改過的非測試檔還原成基底版本（`git checkout <基底> -- <檔>`；新增的檔刪掉），再跑同一批測試：每個都要斷言失敗。照樣通過＝測試沒鑑別力，判未過；變成編譯錯誤、找不到模組或無法收集的，讀斷言判斷，比照 exit `2`。
  5. `git worktree remove --force <scratchpad>/vt-<id>`。

  證據：兩次執行的指令與每個新測試的結果。
- **判讀**（腳本的 exit code；手動驗收比照同樣四類寫結論）：
  - `0` 通過。
  - `1` 未過。「拿掉實作照樣過」＝測試沒鑑別力，修復是改斷言；「有實作卻沒綠」＝實作沒完成。
  - `2` 需人工。多半是新模組被拿掉後測試無法收集。tester 讀這些測試的斷言，確認檢查的是對外可觀察的行為（不是 mock 被呼叫、不是照抄實作算出的值），在證據行寫結論；不合格就判未過。
  - `3` 無法驗證（環境起不來，或 worktree 的測試 import 到主目錄的 code）。判「此標準無法驗證」並寫原因，不判通過。
- **限制**：「新增」只看新增的測試案例，修改既有測試的斷言不在檢查範圍，tester 讀 diff 補看。worktree 與工作目錄共用本機資料庫等外部資源，另一個 session 正在跑測試時不要跑。local-files 會把這張單碰過的實作檔整個還原到基底，之後別張單改過同一檔的內容也會一起被拿掉，紅燈可能不是這張單造成的，遇到時讀輸出判斷。
- **commit**：測試與實作怎麼切 commit 不限，`test` type 照常可用。
- **豁免**：純文件、設定、基礎設施單不附這條；調查單、原型單不附這條；`refactor` 與效能單裡行為不變的優化，以既有測試全綠為證。
