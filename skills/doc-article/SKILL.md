# 把討論整理成技術文章並存進 Notion

## 這個 skill 在做什麼

使用者常常在對話裡解決一個技術問題、做技術選型、或釐清一個概念。討論結束後,這些脈絡很容易就散落在聊天紀錄裡找不回來。這個 skill 的目的,是把整段討論「蒸餾」成一篇日後能直接回顧、甚至分享給同事的技術文章,存進固定的 Notion 資料庫。

重點不是逐字記錄對話,而是**重組**:抓出真正的問題、整理出技術要點、保留關鍵程式碼,並補上讓讀者能帶走的知識點與延伸思考。讀者(可能是三個月後的使用者自己)應該光看這篇文章就懂來龍去脈,不需要回頭翻聊天紀錄。

## 目標位置(Notion)

文章一律寫進這個資料庫:

- 資料庫:**技術文章 Tech Notes**

先用 `notion-search` 找這個名稱的資料庫,取得它的 data source(`collection://...`),再用 `notion-create-pages` 建立頁面,parent 傳 `{"type": "data_source_id", "data_source_id": "<查到的 id>"}`。找不到就問使用者要寫進哪個資料庫,或要不要建一個只有 `標題 Title` 欄位的新資料庫。

**只需要填兩樣東西:標題與內容。** 其他屬性(分類、標籤等)不用管,留空即可。

- `標題 Title`(title 屬性):用一句話講清楚這篇在解決什麼,具體勝過籠統。例:「用 Redis 分散式鎖解決排程重複觸發」優於「Redis 筆記」。
- 內容(頁面 content):按下面的「文章結構」用 Notion-flavored Markdown 寫。

可以順手給頁面一個合適的 emoji icon(依主題選,例如除錯類 🐛、架構類 🏗️、資料庫類 🗄️),但這是加分項,不是必要。


## 工作流程

1. **回顧整段對話**,找出這次討論真正的主軸。一次討論可能岔出多個小主題;判斷哪個是核心,聚焦在它身上。如果真的有兩個各自獨立又夠份量的主題,可以分成兩篇,但多數情況一篇就夠,不要硬拆。

2. **萃取素材**:問題是什麼、試過哪些方向、為什麼某些方向不行、最後怎麼解、過程中冒出哪些值得記住的觀念。把對話裡關鍵的程式碼、指令、錯誤訊息原樣留下來——這些細節日後最有參考價值。同時留意這次跟 AI 協作中值得記下的經驗(見「AI 協作心得」段)。

3. **按下面的結構寫成文章**(用 Notion-flavored Markdown 當頁面 content)。

4. **建立 Notion 頁面**:設定標題與內容即可,其他屬性留空。可順手加個 emoji icon。

5. **回報結果**:給使用者 Notion 頁面連結,並用一兩句話說明寫了什麼。

## 文章結構

頁面 content 一律照這個骨架寫;某個段落若這次討論確實沒有內容(例如完全沒寫到程式碼),就略過該段,不要硬湊或寫「無」。標題用中文、技術名詞保留英文(中英混合)。

```markdown
## TL;DR
一兩句話講清楚問題與最終結論,讓人三秒內抓到重點。

## 背景與情境
這次討論的起點:在什麼情境下遇到這件事、目標是什麼。給足夠的脈絡,讓三個月後的讀者不用回頭翻對話也能進入狀況。

## 問題點
把真正卡住的點講清楚。如果有多個問題,用清單列出。重點是「為什麼這是個問題」,而不只是現象。

## 技術點
這篇的核心。解釋背後的原理、關鍵概念、各個方案的取捨(trade-offs)。這裡要讓讀者學到東西,而不只是照抄結論——說明「為什麼這樣做有效」。

## 解決方案 / 結論
最後採用的做法,以及它如何解決上面的問題。如果有具體步驟,條列出來讓人能照著做。

## 程式碼片段
保留討論中關鍵的程式碼、設定或指令,用標好語言的 code block。每段前面用一句話說明它在做什麼。沒有程式碼就略過整段。

## 知識點 Takeaways
讀者能直接帶走的重點,用清單列 3–6 條。每條是一個獨立、可複用的觀念或經驗法則,而不是針對這次個案的細節。這是文章最該被記住的部分。

## 延伸思考
這次沒深入、但值得後續探索的方向;相關的開放問題、可能的優化、或這個主題還能往哪裡延伸。

## AI 協作心得
選填:只有這次對話出現值得記下的 AI 互動經驗才寫,沒有就略過整段。可能的類型:
- Prompt / 指令寫法:怎麼問一次就對、怎麼問會被誤解、補了什麼脈絡結果明顯變好
- AI 判斷失誤:自信卻答錯、編造 API 或表名、改動超出範圍,以及是怎麼發現的
- 工具與 skill 觸發:哪句話觸發了哪個 skill,有沒有誤觸發或該觸發卻沒觸發
- 驗證方式:用什麼方法確認 AI 產出正確(跑測試、讀原始碼、對真實 DB 驗證)
- 分工界線:哪些適合放手給 AI,哪些必須由人把關
- Context 管理:長對話遺漏脈絡、需要重給背景、memory / CLAUDE.md 是否發揮作用
同樣寫成可複用的經驗法則,附上當時的具體例子。

## 參考連結
討論中提到的文件、文章、issue 連結。沒有就略過。
```

## 寫作品質要點

- **重組而非搬運**:不要把對話一來一往貼上去。讀者要的是整理過的知識,不是聊天紀錄。
- **技術點要解釋「為什麼」**:這是一篇技術文章最有價值的地方。與其寫「我們改用 X」,不如寫「因為 Y,所以 X 比較適合」。
- **知識點要可複用**:「Takeaways」段落要寫成抽離個案後仍然成立的通則,這樣日後遇到類似情境才用得上。
- **程式碼忠實保留**:程式碼、錯誤訊息、設定值照原樣留,標好語言。別自己「優化」改寫,以免失真。
- **中英混合**:用中文敘述,技術名詞(如 race condition、idempotent、connection pool)保留英文,符合工程筆記習慣。
- **標題要具體**:標題決定日後在資料庫裡找不找得到這篇,寫得越具體越好。

## 範例

**情境**:使用者和你討論了 Celery 排程任務在多台 worker 上重複觸發的問題,最後用 Redis 設了一個帶 TTL 的分散式鎖解決。

- 標題:用 Redis 分散式鎖解決 Celery 排程重複觸發(具體、看標題就懂在解決什麼)
- icon: 🔒(加分項)

內容則照上面的結構,把「為什麼會重複觸發(race condition)」寫進問題點、把「為什麼 SET NX 搭配 TTL 能解、TTL 要怎麼抓」寫進技術點、把鎖的程式碼放進程式碼片段、把「分散式系統要假設任務可能被執行多次,所以要設計成 idempotent」這類通則寫進知識點。
