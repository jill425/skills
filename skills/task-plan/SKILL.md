# jill425:task-plan — 規劃並建單

把需求釐清、寫成合規的 task 單。本 skill 的產出只有單。先讀 `${CLAUDE_PLUGIN_ROOT}/contract/task-contract.md`；開 bug、調查、效能、原型單時，再讀 `${CLAUDE_PLUGIN_ROOT}/contract/ticket-kinds.md` 對應的一節。

## 步驟

0. **認後端**：照契約〈Task 後端〉。
   ✅ 完成：知道這個專案的單開在哪、怎麼開。

1. **對齊上下文**：從專案 CLAUDE.md 抓技術棧、程式品質 DoD、路線圖、資料表清單，並依 adapter 列出現有待辦。接著讀需求會碰到的 code：進入點、相關模組、現有的測試，**以 code 為準**。
   ✅ 完成：能說出新單對應路線圖哪個階段、相依哪些既有單；涉及 DB 時手上有權威的資料表清單；需求會碰到的每個檔都指得出 `檔案:行`。

2. **釐清需求**：一次問最關鍵的 1–3 題。跑一下就看得到答案的（現在的行為、輸出、錯誤訊息）自己跑，不問人。需求碰到不熟的模組時，先用 `jill425:code-how` 搞懂現況；要改的地方看起來有特殊理由（防禦性寫法、奇怪的數字、繞路），先用 `jill425:code-why` 查清楚。查到的結論摘要（附 `檔案:行`）寫進 `## 背景`，由此得出的限制寫進 `## 做法`，讓執行者不用重查。
   - **bug 單**：自己重現一次（`ticket-kinds.md`〈bug〉），把觸發方式、實際與期望輸出記下來寫進背景；重現不出來就改開調查單。使用者說「以前可以」時，用 `jill425:code-why` 找出行為是哪次改動變的，寫進背景。
   ✅ 完成：目標、範圍外、驗收樣貌各能用一句話寫出，且沒有一句是猜的。

3. **定種類與顆粒**：照契約〈單的格式〉的種類表決定是功能、bug、調查、效能還是原型單；答案還不清楚、需要先查或先比較的，開調查單或原型單。再照垂直切片的判準決定開幾張、彼此相依。
   ✅ 完成：每張單都有種類，每張都答得出「做完後能看到什麼在跑」。

4. **寫單**：
   - `## 背景` 寫清為什麼，連同這次對話中定案的決策與假設——執行者看不到這場對話。
   - `## 做法` 只寫限制與定案決策，逐步實作留給執行者；SQL／migration／部署才附指令。提到的檔案、函式、欄位都要是這次實際讀過、確實存在的，附路徑。
   - 專案 CLAUDE.md 有程式品質 DoD 時，程式類單的 `## Test 方法` 附「符合專案 CLAUDE.md 程式品質 DoD」一條。
   - 程式類單的 `## Test 方法` 附契約〈Test 方法〉的標準條（豁免也寫在那裡）；bug 單的第一條是重現測試。
   - 要在畫面或服務上看到結果的條件，專案有 `.claude/skills/verify-<app>/` 時就引用它的功能地圖寫（例：「用 verify-<app> 走〈下單〉，證據截圖存在它指定的位置」），讓 tester 照同一套方法驅動真實 app。
   - 專案 CLAUDE.md 有標「待 walking skeleton 驗證」的指令時，第一張單的 `## Test 方法` 附「CLAUDE.md 列出的每條 DoD 指令都實際跑過、全綠，且 CLAUDE.md 已無『待 walking skeleton 驗證』標記」一條。
   - 資料表、欄位等名稱資訊不足標 `<待確認>` 並追問（契約 invariant 2）。
   ✅ 完成：一個只讀這張單和 repo 的人做得出來；每條 Test 能二元判定 pass/fail；每個資料表、欄位名稱有出處。

5. **審查草稿**（純文件、設定單跳過）：把草稿寫進 scratchpad，在同一則訊息裡派出三個 `jill425:task-watcher`，面向各是 `資料`、`影響`、`驗收`；單不碰資料表時省略 `資料`。brief 給三項：照 `${CLAUDE_PLUGIN_ROOT}/skills/plan-review/SKILL.md` 審查、草稿路徑、面向。（同一個 fork 型 skill 連叫幾次會排隊，所以這裡直接派 agent。）報告都回來後：
   - 缺口照補法補進草稿；「影響」報告的影響範圍寫進 `## 做法`。
   - 開發中才會被發現的要求（輸入上限、權限、查詢數）寫成 `## Test 方法` 的條件。
   - 問題留到步驟 6 一次問。
   ✅ 完成：每條缺口都已補進草稿，或註明不補的理由；每個問題都在步驟 6 的清單裡。

6. **摘要過目**：列出要開的單（標題／目標／驗收要點／相依），以及審查留下的問題，每題附選項與建議。使用者的回答寫進草稿。
   ✅ 完成：無殘留 `<待確認>`，每個問題都有答案，且使用者明確同意。同意前⛔ 停在這一步。

7. **落單**：照 adapter 寫出去，讀回對照契約模板，回報單的識別（id 或 iid／網址）。
   ✅ 完成：每張單都讀得回來，四段齊全。

## 修改既有單

適用：改 `## Test 方法`，或使用者要重新審查一張單（例如建單後 code 已經變了、單是審查步驟出現前建的）。

1. 依 adapter 讀全文，連同執行備註與驗收結果。
2. 重新審查時，把單的內容當草稿照步驟 5 審查：缺口補進草稿，問題一次問完。已經開工的單，另外對照分支上已有的 commits。
3. 新舊並列給使用者，⛔ 同意後才改。
4. 依 adapter 就地更新，並在單上註明哪些內容已重新確認。
