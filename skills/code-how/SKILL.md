# jill425:code-how — 這段 code 怎麼運作

產出一份讓不熟這塊的資深工程師讀完就能開始動手的說明：夠建立心智模型，但不是逐行註解。全程唯讀，不改任何檔。

說明只根據實際讀過的 code（契約 invariant 6）。`docs/arch/`、README、註解與記憶只當線索；跟 code 對不上時以 code 為準，並把不一致列進〈坑〉。

派 subagent 照契約〈派 subagent 的慣例〉與〈模型分配〉（`${CLAUDE_PLUGIN_ROOT}/contract/task-contract.md`）。

## 1. 判斷範圍

範圍不清楚時，先說出你的理解再查，使用者會修正。

- **簡單**：單一模組、一個函式、一個窄問題。自己讀 code 回答，直接到步驟 4。
- **複雜**：跨多個檔或服務的子系統、橫切功能、整體架構。走步驟 2。

拿不準時當簡單。

## 2. 派探索者（只有複雜範圍）

把問題切成 2–4 個面向，各是子系統的一塊（例如：進入點與觸發、資料模型與儲存、對外呼叫、錯誤與重試）。同一則訊息派出全部探索者，`subagent_type` 用 `Explore`，模型照「how 探索者」。每個 brief：

> 其他探索者正在平行查同一個子系統的其他面向，不用全部涵蓋，專心把你這一塊查深。不要修改任何檔案。只根據你實際讀到的 code 回報，每個元件與步驟附 `檔案:行`；文件與註解的說法跟 code 不一致時，兩邊都列出來。
> 問題：<使用者的原話>
> 你的面向：<這一塊是什麼、從哪幾個檔或符號開始>
> 回報：
> - **元件**：關鍵的型別、服務、類別；每個寫名稱、檔案路徑、一句話說它做什麼。
> - **流程**：一步一步：哪個函式在哪個檔、做什麼、接著呼叫誰、中間傳什麼資料。
> - **讀過的檔**：全部列出。
> - **邊界**：這塊跟其他部分的接點，輸入和輸出。
> - **不明顯的地方**：反直覺、有歷史原因、容易弄錯的。
> - **沒查清楚的**：誠實列出缺口。

## 3. 派解說者（只有複雜範圍）

全部探索者回來後，派一個解說者（`general-purpose`，模型照「how 解說者」），brief 附上使用者原話與所有探索者的回報，並交代：

> 整合這些回報成一份說明。回報重疊就合併，互相矛盾就自己讀 code 確認。可以讀 code 補缺口，但不用從頭重查。不要修改任何檔案。輸出照下面〈輸出格式〉。

## 4. 輸出格式

依問題取用，用不到的段落省略：

- **概觀**：1–2 段。這是什麼、做什麼、為什麼存在。只讀這段就能判斷要不要往下看。
- **關鍵概念**：讀懂後文需要的型別、服務、抽象，簡短定義。
- **怎麼運作**：最長的一段。什麼觸發、一步步發生什麼、資料去哪、在哪裡分岔。用文字講，指名具體的檔與函式；元件之間有來回或資料要經過幾個階段時，附一張 Mermaid 或 ASCII 圖，文字講得清楚就不畫。
- **東西在哪**：開始動手需要知道的檔案與目錄。
- **坑**：反直覺的行為、歷史包袱、容易踩的地方。

寫法：講具體的東西（「`UserService` 呼叫 `AuthClient.refresh()`」），不講抽象的抽象（「服務委派給客戶端」）。複雜的地方說明為什麼複雜；簡單的不灌水。探索者標出的缺口照實保留，不要藏起來。

## 5. 交回

這次是為了某張單而跑時，把摘要（附 `檔案:行` 或出處）交給呼叫的角色寫進單：建單時寫進 `## 背景`；執行中發現跟單上的理解不同時，寫成〈推翻假設〉或〈決策〉執行備註。不是為了某張單、但結論會影響之後的開發時，建議使用者開一張調查單記下來。


說明本身就是產出。複雜範圍時直接呈現解說者的版本，可以小修讓它更清楚，但不要大改。若這次是為了接下來要改這塊 code 或開單，最後加一段「改動前要注意」：哪些行為必須保留、哪裡最容易改壞。
