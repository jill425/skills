# jill425:plan-review — 這張單漏了什麼

參數：`$ARGUMENTS`（草稿檔路徑、面向：`資料`｜`影響`｜`驗收`）。

草稿還沒有 code。要找的是「照這張單做下去，做到一半才會發現」的事：單上沒定的決定、不成立的前提、沒有人負責的要求。

1. **讀草稿與現況**：讀草稿全文、專案 `./CLAUDE.md`，以及草稿提到的每個檔案、資料表、API 的實際內容，**以 code 為準**。
   ✅ 完成：草稿提到的每個檔案、欄位、函式都實際讀過，對不上的記下來。

2. **照面向逐項查**，只做參數指定的那一個：
   - **資料**：要新增或改的資料表與欄位——型別、長度、collation 與大小寫、NULL 與預設值、唯一性；DDL 對既有資料的影響；同一筆資料被同時寫入、重試、中途失敗時的結果；每個輸入的長度與數量上限。
   - **影響**：要改或刪的 API 欄位、資料表、共用模組各有哪些消費者（前端、App、報表、排程、其他服務、既有測試），照 `${CLAUDE_PLUGIN_ROOT}/skills/code-impact/SKILL.md` 步驟 2–3 找出改動安全所依賴的事實；誰能呼叫、要不要驗身分與權限；碰不碰密鑰與個資。
   - **驗收**：每一句目標有沒有一條 Test 方法能證明它；每條 Test 方法能不能二元判定；缺的邊界與錯誤情況；使用者實際等待的路徑上，查詢數與資料量會不會隨輸入成長。
   ✅ 完成：該面向的每一項都有結論：沒問題、缺口，或要問使用者。

3. **分類**：
   - **缺口**：code 或文件裡查得到答案的，寫出答案與出處，可以直接補進單。
   - **問題**：答案取決於使用者要什麼的，寫成選擇題，附選項、你的建議、選錯的代價。會改變資料語意或對外行為的（大小寫、上限、權限、錯誤時回什麼）一律列為問題，你有把握的答案寫在建議裡。
   ✅ 完成：每一條都歸進缺口或問題。

## 報告

```
面向：<資料｜影響｜驗收>
影響範圍：<這張單會動到的資料表、API、共用模組；只有「影響」面向要填>
缺口：
1.〔<證據等級>〕<單上缺什麼> — 補法：<寫進哪一段、寫什麼>。證據：<`檔案:行` 或指令與輸出>
問題：
1. <問題> — 選項：<A｜B>；建議：<哪個、為什麼>；選錯的代價：<做到哪一步才會發現、要重做什麼>
```

兩段合計最多 5 條，依「做到一半才發現的代價」排序；某一段沒有就寫「無」。
