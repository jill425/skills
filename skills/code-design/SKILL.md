# jill425:code-design — 先設計介面再寫

改動跨越函式或模組邊界時，先把「呼叫端怎麼用、型別長怎樣、誰負責什麼」定下來，再填實作。只改一個函式內部的單不需要這支。

派 subagent 照 `${CLAUDE_PLUGIN_ROOT}/contract/dispatch.md`；設計原則照 `${CLAUDE_PLUGIN_ROOT}/contract/principles.md`。

## 1. 搞懂周圍

讀這次會碰到的每個系統：用 `jill425:code-how` 產出說明；設計會改變既有的分層或歸屬時，再用 `jill425:code-why` 查現在的形狀是為了什麼，查到的理由當成限制。全新、沒有周圍系統要整合的才跳過。

✅ 完成：說得出新 code 會被誰呼叫、會呼叫誰、有哪些不能動的限制，各附 `檔案:行`。

## 2. 至少畫兩個方案

同一則訊息派兩個設計者，模型照「設計者 A」「設計者 B」（預設不同模型）。每個設計者在自己的 worktree 或 `<scratchpad>/design-<n>/` 工作，brief 給需求、步驟 1 的結果，以及：

> 產出一個設計方案。不要寫實作，函式本體一律寫成「未實作」（例如 `raise NotImplementedError`），難的邏輯用註解寫虛擬碼。
> 1. **先寫呼叫端**：像 README 一樣寫用法，再寫兩三個真實的呼叫處。用法就是規格，型別從它推出來；兩者對不上時改型別，不改用法。
> 2. **資料結構先定**：核心型別定好後，把每個主要的存取方式走一遍；需要「之後再加個 map 或快取」代表結構錯了。
> 3. **介面要深**：用小而簡單的公開介面，把複雜度藏在裡面。外部的格式（傳輸、資料庫、框架的型別）不出現在公開介面上，在介面後面解析成領域型別。
> 4. **共享狀態**：兩個執行者可能同時寫同一份狀態時，預設各自持有、讀的時候再合併。
> 5. **不變條件寫進型別**：不容易用錯的型別 > 執行時檢查 > 註解。
> 6. **呼叫鏈短**：追一個流程要讀超過三個檔，就把層級攤平。
> 回報：用法與呼叫處、型別與簽名、模組分工、一段理由（為什麼這樣分、放棄了什麼）。做出你能做的最好設計，不要往中間靠——方案之間的差異正是用來比較的。

兩個方案要在**整體結構**上不同（例如誰擁有狀態、模組怎麼切），不是同一個結構裡的小差異。都長得一樣就再要一個不同方向的。

## 3. 篩選與比較

每個方案先對照下面的設計警訊，中了就修改或淘汰：

| 警訊 | 怎麼看出來 |
|---|---|
| 淺模組 | 呼叫端要依序叫好幾個方法才完成一件事；公開選項暴露內部階段；學會介面還是得懂實作 |
| 資訊外洩 | 同一個內部決定（格式、規則、協定細節）出現在好幾個模組，改一處要同步改多處 |
| 照執行順序切模組 | 載入、驗證、轉換、儲存各一個模組，同一份資料與規則在各階段重複 |
| 原樣轉傳 | 方法只是把一樣的參數轉給另一個一樣形狀的方法，多一層卻沒藏住任何東西 |
| 擁有權分散 | 不只一個模組寫同一份狀態，或各留一份副本 |
| 同一件事兩種做法 | 新的呼叫端會照抄先找到的那種，兩種都一直長 |
| 內部可被 import | 外面能直接 import 內部，最短路徑就會變成介面的一部分 |
| 手動同步的清單 | 加一個項目要改好幾個清單 |

再比**介面深度**：同樣的能力，公開面越小越簡單越好。以**照抄者**為前提（見 `principles.md`），選照抄者從一個檔看起來對的改法、對整個 repo 也對的那個。選一個當基底，另一個值得的部分移植過來（通常一兩點），手動融進去，讓結果仍是一個一致的設計。

✅ 完成：有一個選定的設計，以及選它、不選另一個的理由。

## 4. 記下來

- 選定的用法、型別與簽名先 commit 成一個骨架（函式本體仍是未實作），讓後面的實作有明確的契約。
- 為某張單而做時，寫一筆〈決策〉執行備註：選了哪個方案、為什麼不選另一個、移植了什麼。

## 5. 照設計實作

把未實作的本體換成程式。設計就是契約：實作時發現需要設計沒預料到的參數或形狀，先判斷是設計錯了、需求漏了、還是實作做過頭了，再改；偏離設計時寫一筆〈偏離做法〉執行備註。

## 6. 設計錯了就重來

一兩個例外不代表設計錯。出現下面這些**重複的模式**時，丟掉設計回到步驟 1，不要在錯的設計上一直補：

- 同一種繞路寫法在不相關的地方反覆出現。
- 幾個不相關的邊界情況都需要特殊分支。
- 型別要靠 `Any`、強制轉型、「其實一定有值」的選填欄位才編譯得過。
- 設計說狀態沒有共享，實作卻一直想加鎖。
- 呼叫端得知道抽象的內部規則才用得對。

重來時把新的限制當成一開始就知道的事重新設計，先刪再加：新設計在變大之前應該比舊的小。
